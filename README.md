# 냉장고 털이 v0.9.20 · 2026-11-15

이 앱은 혼자 생활하는 자취생을 대상으로 합니다. 화면에서 먹을 사람 수를 선택하지 않으며, 새 식사 계획·추가 구매 추천·수량 비교·조리 기록은 1인분 기준입니다. 사용자는 실제 사용량만 수정합니다. 원본 레시피의 기준 인분은 원문 수량을 1인분으로 환산하기 위한 별도 정보이며, 원문에 없으면 임의로 추정하지 않습니다. 이전 여러 인분 계획은 보관하되 새 1인분 계획을 생성하도록 안내합니다.


팀에서 확정한 네 가지 기능과 랭킹 설명 접기를 구현했습니다. OCR·관리자 기능은 이번 범위에 포함하지 않습니다.

교수님 검토 순서와 현재 범위는 **교수님_검토안내.md**를 먼저 참고하세요. 실행 파일은 이 폴더 바로 아래 index.html입니다. 이전 버전 하위 폴더와 구분합니다.

## 최종 검토 정리

홈은 냉장고 활용·레시피 추천·요리 기록으로 구분했습니다. 상세 화면은 냉장고 비교·원문·사용자 기록·출처/API 설명을 구분하고 긴 설명은 펼쳐봅니다. 단위·조사·빈 값·입력 이름을 정리하고 카드의 키보드 탐색과 작은 화면의 줄바꿈을 보완했습니다.

이번 주는 홈과 랭킹 모두 월요일부터 집계합니다. 내 레시피·삭제는 작성자 ID로 구분합니다. 기존 소유자 ID가 없는 사용자 자료는 임의로 현재 사용자 소유로 간주하지 않습니다. 삭제 ID는 interactions_user.json의 삭제 이력에 포함해 파일에서 다시 읽어도 복원되지 않게 합니다. 새 레코드 ID는 삭제 이력과도 겹치지 않습니다. 이 구분은 클라이언트 동작 보호이며 서버 권한 검증은 아닙니다.

조리 시간·기준 인분의 입력 범위를 검사하고, 저장 실패·삭제된 레시피·새 게시물의 사진 초기화·완료 후 재료가 없는 계획도 처리합니다.

## 실행

이 폴더에서 `python -m http.server 8000` 실행 → `http://localhost:8000`. HTML 더블클릭(file://)은 JSON fetch가 제한됩니다. 정적 호스팅도 가능합니다.

## 플래그와 필드 출처

- J / meta.source=json: 저장 원본.
- A / meta.source=api: API 조회 명세 또는 응답. 명세는 status=not_requested이며 응답값이 없습니다. 실제 기록은 success/error로 구분합니다.
- U / meta.source=user: 사용자 입력 또는 팀 작성 참조 사전.
- C / meta.source=calc: 연결·추천·집계 결과. 별도 수집 출처가 아닌 계산 결과 구분입니다.

meta.real/user/api/calc/empty 배열로 최상위 및 중첩 필드 경로를 분류합니다. null은 empty에만 넣고 각 필드는 한 분류에만 속합니다. meta 자체는 설명이므로 분류에서 제외합니다. 사용자 입력이라고 해서 검증된 사실을 뜻하지는 않습니다.

## API 표시

카드는 **J + API 조회 가능**을 표시합니다. 상세는 저장 JSON을 먼저 표시하고 식약처 COOKRCP01 API에 요청합니다. 응답 이름과 RCP_SEQ가 원본 이름·ID에 모두 일치할 때만 적용합니다. 실제 수신한 영양정보·사진·팁에만 **API** 태그를 붙입니다. 실패하거나 필드가 비면 **JSON 원본 유지**로 표시합니다. API 정보에 요청 시각·성공 여부·원본 ID 또는 실패 원인을 보여주며 실제 원문과 적용값을 기록합니다. API 키는 기록·내보내기에 넣지 않습니다.

키·네트워크·CORS에 따라 실요청이 실패할 수 있습니다. 이번 검사는 실제 접속 성공 확인이 아닌 격리된 응답 모의 검사입니다. 배포 도메인에서 실제 API 결과를 확인해야 합니다.

## 더미 정리

팀 작성 시연 레시피 24건, AI 레시피 210건, 예시 냉장고, 미검증 대체 재료를 실행·배포 자료에서 제외했습니다. 기존 식약처 76건의 규칙 기반 시간·난이도는 null로 변경했습니다. 옛 CSV/XLSX 및 더미 생성·변환 도구도 새 구조를 덮어쓰지 않도록 배포에서 제외했습니다. 변경 전 자료는 다운로드의 원본 ZIP을 보관하세요. 원본에 식약처 출처로 기록된 내용 전체를 외부 기관과 재대조한 것은 아닙니다.

## 사용자 데이터 저장

Firebase는 기존처럼 로그인·회원 프로필에 사용합니다. 레시피·냉장고·게시물 등은 브라우저 localStorage에 JSON으로 저장됩니다. 정적 웹은 data/ 파일을 자동 수정할 수 없습니다. **마이 → 데이터 명세**에서 개별 JSON 또는 전체 스냅샷을 내려받아 개발 폴더에 반영합니다. 비밀번호·계정 해시·세션·설정·API 키는 내보내지 않습니다. 해당 브라우저 저장 키가 없을 때 실제 사용자 JSON을 초기 자료로 읽습니다. 다중 기기 동기화와 사용자별 전체 데이터 격리는 이번 수정 범위에 포함하지 않았습니다. 식사 계획만 로그인 사용자별 키를 사용합니다.

## 식사 계획

홈 → 식사 계획 만들기. 하루 한 끼, 최대 7끼를 추천합니다. 확인된 기준 인분·단위가 있는 레시피는 1인분 기준으로 필요한 양을 계산하고 가상 재고에서 순차적으로 차감해 예상 잔여량을 표시합니다. 앞 끼니에 쓸 재료를 뒤 끼니에 중복 배정하지 않습니다. 확인된 수량이 부족하면 해당 레시피를 계획에서 제외합니다. 원문 수량·인분이 미확인인 추천은 조건부로 표시하며 정확한 잔여량을 주장하지 않습니다.

계획만 만들면 실제 냉장고는 바뀌지 않습니다. 각 끼니의 ‘조리 완료 · 사용량 확인’에서 실제 사용량을 확인한 뒤 재고에 반영합니다. ‘완료한 끼니를 남기고 다시 계획’으로 변경된 냉장고에 맞춰 남은 끼니를 다시 추천받습니다.

## 수량 기반 냉장고 및 조리 완료

1. 냉장고의 남은 양을 `150g`, `0.5kg`, `2개`, `0.5모`처럼 등록합니다. 기존 자유 입력도 보존하지만 파싱되지 않는 값은 수량 확인 필요로 표시합니다.
2. 레시피 상세에서 필요량·보유량·부족량을 봅니다. 원문에 기준 인분이 없으면 ‘레시피 수량 기준 확인·수정’에서 직접 확인한 기준 인분과 재료별 수량을 저장합니다. 원본은 변경하지 않고 사용자 확인 JSON에 별도로 저장합니다. 레시피 등록 시에도 기준 인분을 입력할 수 있습니다.
3. g↔kg, mL↔L만 환산하며 모↔g, 컵↔mL, g↔mL 같은 근거 없는 변환은 하지 않습니다. 원문이 모호하면 직접 확인합니다. ‘조리 가능’은 등록된 수량·기한 기준의 재료 비교 결과이며 조리 도구 등 다른 조건은 판단하지 않습니다.
4. ‘조리 완료’에서 실제 사용량을 수정·확인합니다. 부족량·단위 오류·변경된 재고는 차감을 막습니다. 여러 저장 중 하나라도 실패하면 이전 JSON을 복원합니다. 같은 완료 기록이나 완료된 계획 끼니를 두 번 차감하지 않습니다.
5. 로그인 후 기록한 조리 완료는 요리 게시물에 연결할 수 있습니다. 게시물에는 실제 사용 재료와 당시의 임박 여부를 표시합니다. 기록 하나는 게시물 하나에만 연결하며 게시물 등록은 재고를 다시 차감하지 않습니다. 비로그인 기록은 guest로 남으며 로그인한 다른 작성자의 게시물에 연결하지 않습니다.

상단 냉장고 버튼은 어느 화면에서나 냉장고로 연결되고, 임박 재료가 있을 때만 수량 배지가 나타납니다. 홈의 임박 안내에서도 바로 냉장고를 열 수 있습니다.

## 이것 하나만 사면

홈에서 혼자 먹는 한 끼를 기준으로 필요한 재료 중 한 종류만 부족한 레시피를 묶어 추가할 재료를 제안합니다. 기존 재료를 더 활용하는 조합과 임박 재료 활용을 고려합니다. 수량이 확인된 추천은 레시피별 추가 필요량을, 미확인 추천은 ‘재료명 기준 · 확인 필요’를 표시합니다. 물·양념도 실제 등록된 재료만 보유로 판단합니다. 여러 대안 레시피의 추가량을 전부 동시에 조리하는 총 구매량으로 합산하지 않습니다.
